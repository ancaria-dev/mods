# mods

Это официальный реестр модов для Sacred Gold и исходный код четырёх модов.
Лаунчер знает адрес реестра изначально. Откройте вкладку Available, нажмите
Install, и проверенный jar попадёт в `<Sacred Gold>/mods`. Скачивать и
перекладывать файлы вручную не требуется.

Официальным реестром выбор не ограничен. Лаунчер принимает HTTPS-ссылку для
клонирования, оканчивающуюся на `.git`, и читает
`sacred.mods.repository.json` из корня репозитория. Для приватного репозитория
можно указать токен доступа.

## Что здесь есть

| Мод | Что делает |
|---|---|
| [`self-check`](self-check) | Подписывается на все события загрузчика и показывает окно с 20 сценариями. Белый означает, что сценарий ещё не проверен, зелёный отмечает успех, а красный сообщает о неожиданном результате. Для событий с ответом мод проверяет весь путь от игры до JVM и обратно. |
| [`tracer`](tracer) | Записывает каждое событие в `<Sacred Gold>/logs/logs-<time>.txt`, по одному файлу на запуск. Все обработчики работают с приоритетом `MONITOR`, поэтому Tracer видит окончательный ответ и не может его изменить. |
| [`old-huge-potions`](old-huge-potions) | При подборе заменяет каждое зелье игрока на полноразмерный тип той же разновидности. Таблица строится по именам типов запущенной игры. Цена предмета не меняется. Влияние замены на лечение пока не подтверждено. |
| [`all-my-runes`](all-my-runes) | При подборе заменяет руну чужого класса копией одной из уже встреченных рун героя. Сначала нужно подобрать собственную руну. Неизвестные руны мод оставляет без изменений. |

В дескрипторе `self-check` указаны конфликты с `old-huge-potions` и
`all-my-runes`. Все три мода отвечают на событие подбора и могут переписать один
предмет, поэтому итог зависит от последнего обработчика. Лаунчер убирает обе
стороны такого конфликта из списка установки. Эти моды всё ещё можно установить
вручную, если вы сознательно принимаете такой порядок работы.

## Как собрать

Нужен JDK в `PATH`. Плагин компилирует моды для Java 21.

```
gradlew assembleSacredMod
```

Команда собирает все четыре мода, проверяет каждый jar линтером и кладёт
результаты в `<мод>/build/sacred-mod/`. Для установки прямо в игру выполните:

```
gradlew installSacredMod -PsacredDir="C:/Games/Sacred Gold"
```

Плагин `dev.ancaria.coderpack` и API разрешаются как опубликованные зависимости,
а не через соседние каталоги. Первого релиза пока нет, поэтому сборка ищет их в
Maven Local. Сначала выполните `publishToMavenLocal` в репозиториях `build` и
`coderpack`. CI делает то же самое в отдельных чекаутах этих репозиториев.

## SRML

Sacred Repository Mod Layout, версия 1. Реестр определяется файлом
`sacred.mods.repository.json` в корне репозитория. Текущая структура выглядит
так:

```
sacred.mods.repository.json   что здесь есть, генерируется
registry.toml                 кто мы такие, пишется руками
icon.png                      картинка реестра
<id>/                         каталог мода: код, build.gradle.kts, icon.png
```

Каждый мод остаётся обычным Gradle-проектом. В реестре с несколькими модами
каталог обычно называют по идентификатору мода. По этому соглашению
`coderpack index` добавляет относительные пути `source` и `icon`. При другом
имени каталога эти поля отсутствуют. В реестре из одного мода корневой
`icon.png` может служить иконкой самого мода.

Индекс не редактируют вручную. Идентификатор, название, версия, описание,
диапазоны API и загрузчика, авторы, сайт и конфликты копируются из
`META-INF/declaration.toml` внутри каждого собранного JAR-файла. Необязательные
поля отсутствуют, если дескриптор или структура каталогов их не задают. Название,
описание, сайт, иконка и шаблон URL реестра берутся из `registry.toml`. Имя
JAR-файла, размер в байтах, SHA-256 и URL загрузки вычисляются по артефакту и
шаблону.

```
coderpack index           перегенерировать
coderpack index --check   то, что делает CI
```

После изменения версии нужно заново собрать мод и выполнить `coderpack index` в
том же коммите. Команда с `--check` ничего не записывает и завершается с кодом
1, если сохранённый индекс не совпадает с собранными JAR-файлами. Генератор
также отказывается добавлять JAR-файл, который не прошёл проверку мода.

## Как выходят релизы

Каждому моду соответствует отдельный релиз GitHub с тегом
`<id>-v<version>`. В него загружается JAR-файл этого мода. В ветке `master`
workflow собирает все четыре мода, проверяет сохранённый индекс и создаёт релиз,
только если такого тега ещё нет. Если версии не изменились, новых релизов не
будет.

Индекс хранит URL, размер и SHA-256 каждого JAR-файла. Перед установкой лаунчер
сверяет хеш, читает дескриптор из загруженного файла и проверяет идентификатор и
совместимость с загрузчиком. Файл, не прошедший проверку, в каталоге модов не
останется.

Свой реестр собирается по той же схеме. Заполните в `registry.toml` название,
сайт и шаблон URL релизов, соберите JAR-файлы и запустите `coderpack index`.
После этого реестр можно добавить в лаунчер по HTTPS-ссылке для клонирования.
